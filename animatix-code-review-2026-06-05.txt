### 🟡 中等问题

#### 1. Typst raw block 转义可能不充分

**文件**: `renderer/text.rs:316-318, 339-341`  
**问题**: 新代码用 Typst raw inline `` `text` `` 包裹用户文本。如果用户文本包含连续的反引号（如 ` `` `），Typst raw block 的定界符匹配可能失败；Typst raw inline 不能跨行，换行符可能导致解析失败。  
**建议**: 使用 Typst 块级 raw（三重反引号 ```），或对换行符单独处理。

#### 2. `require_ffmpeg()` 在视频导出入口无条件调用

**文件**: `video.rs:310, 474`  
**问题**: 即使用户不导出音频，视频导出也会因缺少 ffmpeg 而失败。如果系统只有 libavcodec 没有 ffmpeg CLI（某些嵌入式场景），这会误报。  
**建议**: 只在实际需要音频 mux 时才检查。

#### 3. `layout.rs` 静默吞错

**文件**: `layout.rs:125-133, 232-241`  
**问题**: 旧代码在 track 缺失或 layout_size 未 seed 时会 panic（`expect`），暴露数据完整性问题。新代码 `filter_map` 静默跳过缺失子项，可能导致布局容器中子项神秘消失。  
**建议**: 添加 `tracing::warn` 记录被跳过的子项。

#### 4. `for_iteration_count` 作用域过宽

**文件**: `vm.rs`  
**问题**: `for_iteration_count` 是 `ModifierVm` 级别字段，跨多个 for-loop 共享。如果 modifier 代码中有多个嵌套或顺序 for-loop，计数器不会重置。100,000 的限制在单个循环中足够宽松，但在多循环场景下可能比预期更早触发。

#### 5. 场景缓存双 clone

**文件**: `scene_eval.rs:779-795`  
**问题**: `scene.clone()` 做缓存 + 再 `.clone()` 做返回值，对于大型场景两份完整 clone 可能成为性能热点。注释承认了问题但未修复。  
**建议**: 考虑 `Rc<Scene>` 减少为一次引用计数递增。

#### 6. 全量缓存淘汰

**文件**: `renderer/text.rs:588-590`  
**问题**: `self.cache.len() > 1000` 时 `self.cache.clear()` 一次性清空 1000 条，下次编译需要重新计算 Typst 帧，导致渲染卡顿。  
**建议**: 使用 LRU 淘汰或更渐进的方式。

## 二、animatix-syntax（crates/animatix-syntax/）

**变更**: 从 `to_source.rs`（965→525 行）和 `formatter.rs`（521→269 行）提取共享格式化逻辑到新文件 `format_core.rs`（583 行），修复 `source_index.rs` bug，移除 `ast.rs` 死代码。

### 🔴 高优先级

#### 1. 双重缩进 bug — 嵌套 actor 输出缩进翻倍

**文件**: `format_core.rs:269-278, 307-318`  

```rust
if !children.is_empty() {
    let children_str = children
        .iter()
        .map(|c| format_inline_item(c, depth + 1, indent_size))  // ← 缩进 #1
        .collect::<Vec<_>>()
        .join("\n");
    let indented = indent(&children_str, depth + 1, indent_size);  // ← 缩进 #2
    parts.push(format!(" {{\n{}\n{}}}", indented, " ".repeat(indent_size * depth)));
}
```

**问题**: `format_inline_item` 已经对输出应用了 `indent(raw, depth, indent_size)`，然后 `format_actor_like` 又对整个 children 字符串应用了一次 `indent(...)`，导致**双重缩进**。旧代码中每个 `InlineItem` 变体自己处理格式化，只调用一次 `indent(&children_str, 1)`。

同样的 bug 存在于 `InlineItem::SlotFill` 处理（line 307-318）。

**影响**: 任何包含嵌套容器（actor 内嵌 actor）的 `.amx` 文件都会输出错误缩进。现有 roundtrip 测试只校验 `parsed.len() == reparsed.len()`（数量相等），不校验内容正确性，因此未捕获此问题。

**修复方案**: 从 `format_inline_item` 移除缩进，使其产生原始文本（类似 `format_stmt_raw`）：

```rust
fn format_inline_item_raw(item: &InlineItem, depth: usize, indent_size: usize) -> String {
    match item {
        InlineItem::Anonymous { ty, props, modifiers, children } =>
            format_actor_like(None, true, ty, props, modifiers, children, depth, indent_size),
        InlineItem::Labeled { label, ty, props, modifiers, children } =>
            format_actor_like(Some(label), false, ty, props, modifiers, children, depth, indent_size),
        InlineItem::SlotMarker => "@slot".into(),
        InlineItem::SlotFill { slot, items } => {
            let items_str = items.iter()
                .map(|i| format_inline_item_raw(i, depth + 1, indent_size))
                .collect::<Vec<_>>().join("\n");
            format!("@{} {{\n{}\n{}}}", slot, items_str, " ".repeat(indent_size * depth))
        }
    }
}

pub fn format_inline_item(item: &InlineItem, depth: usize, indent_size: usize) -> String {
    let raw = format_inline_item_raw(item, depth, indent_size);
    indent(&raw, depth, indent_size)
}
```

然后在 `format_actor_like` 中使用 `format_inline_item_raw` 处理 children 并移除第二个 `indent()` 调用。

### 🟡 中等问题

#### 2. `format_stmt_raw` 对 `ActorDecl` 返回已缩进文本

**文件**: `format_core.rs:348-357, 370-394`  
**问题**: `format_stmt_raw` 文档约定产出原始文本（无前导缩进），但对 `Stmt::ActorDecl` 委托给 `format_actor_like`，后者内部自行应用 `indent(...)`。当 `format_stmts_raw` 再次用 `indent(raw, depth)` 包裹时，子项缩进变为 `indent_size * (2*depth + 2)` 而非预期的 `indent_size * (depth + 2)`。  
**修复**: 级联自上面的 Bug #1，修复双重缩进后此问题自动解决。

#### 3. `Formatter::default()` 遮蔽 `Default` trait

**文件**: `formatter.rs:68-70`  
**问题**: 手动实现 `default()` 作为固有方法而非 `impl Default for Formatter`。使用 `Formatter::default()` 的直接调用可以工作，但泛型代码中 `T: Default` 无法识别。  
**修复**:
```rust
impl Default for Formatter {
    fn default() -> Self { Self::new(FormatConfig::default()) }
}
```

#### 4. `parse_snippet` 死错误处理代码

**文件**: `parser/mod.rs:156-166`  
**问题**: 两个分支返回值完全相同：
```rust
if errors.is_empty() {
    ast
} else {
    // Try harder: some snippets omit trailing braces / are fragments.
    // Fallback: return whatever parsed.
    ast  // ← 与成功分支完全相同
}
```
**建议**: 移除错误检查，或真正实现 "try harder" 回退逻辑（如添加合成右括号后重试）。

### 🟢 低优先级

#### 5. 字符串序列化未转义反斜杠

**文件**: `format_core.rs:144-147`  
**问题**: 仅转义双引号 `\"`，未转义反斜杠 `\`。当前 parser 以原始字符存储，round-trip 安全，但未来 parser 变更（如取消转义）时会产生错误输出。  
**建议**: 添加 `s.replace('\\', "\\\\").replace('"', "\\\"")` 以增强鲁棒性。

#### 6. 浮点数边界 case

**文件**: `format_core.rs:49, 137`  
**问题**: `s.fract() == 0.0` 对 `3.0000000000000004` 这类浮点值不会匹配为整数。`*n as i64` 对超出 i64 范围的 f64 值会静默饱和。  
**建议**: 使用 epsilon 检查 `(s - s.round()).abs() < 1e-9`。

#### 7. O(n²) 前导空行移除

**文件**: `formatter.rs:92-94`  
**问题**: `result.remove(0)` 每次 O(n) 移位，对大量前导空行文件为 O(n²)。  
**建议**: 使用 `result.drain(..n)` 或找到首个非空索引后切片。

**文件**: `lib.rs`  
**问题**: `SymbolTable::build_from_ast` 以 `line: 0, col: 0` 收集 scenes，但 `walk_for_positions` 中没有 `"scene_definition"`（或等效 tree-sitter 节点类型）的处理分支。这意味着 **scenes 将永远拥有 `(0, 0)` 位置**，导致 go-to-definition 对 scenes 返回文件头——一个错误的位置。

### 🟡 中等问题

#### 2. `source` 参数传入 `check_stmt` 但从未使用

**文件**: `diagnostics.rs:205, 287`  
**问题**: `source: &str` 被添加到 `collect_semantic_diagnostics` 和 `check_stmt`，但在 `check_stmt` 内部从未被读取。仅传递给递归调用。属于死代码/未使用参数。

#### 3. AST span vs tree-sitter 位置来源不一致

**文件**: `diagnostics.rs`  
**问题**: `check_stmt` 中位置来自 `span_to_diag(span)`（使用 AST span，来自 chumsky parser），但 `collect_semantic_diagnostics` 中重复标签、未使用标签、缺失导入的位置来自 enriched symbol table（tree-sitter 位置，通过 `enrich_positions`）。两个来源可能不一致。  
**建议**: 统一使用 symbol table 的 enriched positions，或确保 AST spans 始终被填充。

#### 4. `check_stmt` 诊断位置指向整个语句而非特定 token

**文件**: `diagnostics.rs`  
**问题**: 对于 `Stmt::Action`、`Stmt::Assignment`、`Stmt::ActorDecl`，诊断位置使用**语句级别的 span** 而非定位到具体的违规 token（如动作动词、目标标签、特定属性）。同一语句上的多个诊断将高亮相同范围，降低用户体验。

#### 5. `diagnostics()` 每次调用 clone `type_diagnostics`

**文件**: `lib.rs:371`  
**问题**: `diagnostics.extend(self.type_diagnostics.clone())` 每次调用 `diagnostics()` 或 `diagnostics_with_config()` 时都 clone 整个 `Vec<Diagnostic>`。这与 commit `402366d` 的性能优化意图矛盾。  
**建议**: 将 type diagnostics 一次性合并到缓存诊断中，或改为引用返回。

#### 6. Dirty flag 与 `update()` guard 冗余

**文件**: `lib.rs`  
**问题**: `update()` 已检查 `if self.source == source { return; }`（line 83）。`dirty` 标志在 `rebuild_symbols()` 被调用时**始终为 true**，因为 `update()` 在调用 `rebuild_symbols()` 前设置了 `self.dirty = true`。`rebuild_symbols()` 内部的 dirty guard（line 125）永远不会跳过类型检查器。dirty 标志仅在 `rebuild_symbols()` 可独立调用时有意义（如从已移除的 `set_workspace()` 方法）。

#### 7. `import_path.exists()` 违反 "No I/O" 设计原则

**文件**: `diagnostics.rs:254`  
**问题**: 诊断检查器中的 `import_path.exists()` 文件系统调用违反了 `lib.rs` line 12 中声明的 "No I/O" 设计原则。使诊断依赖文件系统状态，在 LSP 文件编辑场景下可能产生问题。

#### 8. 别名 import 污染全局命名空间

**文件**: `workspace.rs:71-78`  
**问题**: `resolve_symbols` 中 `if import.alias.is_some() { ... } else { ... }` 的两个分支都执行 `merged.merge(&entry.symbols)`。别名分支有注释说明命名空间追踪但实际未实现。别名导入将污染全局命名空间，可能导致符号名冲突。  
**状态**: 已知 TODO。

## 四、animatix-gui（crates/animatix-gui/）

**变更**: 20 个提交（Phase 0.5 到 Phase 6 全部 GUI 功能），代码量最大

### 🔴 高优先级

#### 1. `handle_distribute_actors` 中 NaN 导致 panic

**文件**: `handlers/actor.rs:360-361`  
```rust
Axis::Horizontal => rects.sort_by(|a, b| a.1.x0.partial_cmp(&b.1.x0).unwrap()),
Axis::Vertical => rects.sort_by(|a, b| a.1.y0.partial_cmp(&b.1.y0).unwrap()),
```

**问题**: commit `385fe54` 声称修复了 "NaN-safe sort"，但此处仍使用 `.unwrap()`。如果任何 `kurbo::Rect` 的坐标包含 NaN（通过用户编辑或异常值传播），将导致**运行时 panic**。  
**修复**: 使用 `unwrap_or(std::cmp::Ordering::Equal)` 或 `total_cmp`，与 `sidebar.rs:448` 中的处理方式一致。

#### 2. Find/Replace All 绕过 AST 管道

**文件**: `shell/find_replace.rs:105-127`  
```rust
fn perform_find_replace_all(&mut self) {
    let new_text = text.replace(find, replace);
    self.document_store.source.editor.replace_text(new_text.clone());
    self.document_store.source.document.source_text = new_text;
    // 但没有更新 raw_statements 或 source_index
}
```
**问题**: Replace All 直接操作纯文本字符串，完全绕过 `SourceEdit` / `apply_edit` 管道。结果：
- `raw_statements`（AST）与 `source_text` 不同步
- `source_index` 未重建
- 下次 rebuild 时重新解析，但 rebuild 前如有操作依赖 AST（如 inspector），会出现不一致
- undo 栈中快照记录的是 Command 而非文本 diff，可能导致 undo 后丢失替换  
**建议**: 替换后至少调用 `invalidate_cache()` 或触发解析。

#### 3. `insert_property` 返回错误的 Error 变体

**文件**: `source_edit/actor_edits.rs:47-52`

#### 4. `stmt_to_inline_item` 对非 ActorDecl 语句数据丢失

**文件**: `source_edit/actor_edits.rs:259-266`

#### 5. "Open Settings" 映射到 dummy action

#### 6. "Duplicate Selected" 只复制第一个选中 actor

#### 7. `delete_actor` 仅删除顶级声明

#### 9. Scene 拖拽排序 off-by-one

**文件**: `sidebar.rs:544`  
```rust
if from_idx != to_idx && to_idx <= scene_names.len() {
    let mut new_order = scene_names.clone();
    let removed = new_order.remove(from_idx);
    let insert_at = if to_idx > from_idx { to_idx - 1 } else { to_idx };
    new_order.insert(insert_at.min(new_order.len()), removed);
}
```
**问题**: `to_idx <= scene_names.len()` 允许 `to_idx == scene_names.len()`。`insert_at.min(new_order.len())` 防止越界 panic，但在 `to_idx == len` 且 `from_idx < to_idx` 时，`insert_at = len - 1`，可能不是用户预期的"移到末尾"。
